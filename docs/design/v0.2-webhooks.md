# FlowGuard v0.2: webhook testing (design)

Status: **approved**. Milestone 1 implemented; it ships as **v0.2.0**.
Milestone 2 is not started and is rescheduled to **v0.3.0**.

Release scope (decided 2026-10-28): v0.2.0 contains Milestone 1 only.
Everything marked Milestone 2 or [M2] below (delays, retries, timeout
simulation, HMAC signing, state polling) is planned for v0.3.0. The file
name keeps "v0.2" because the design was approved as one document.

## Scope and non-goals

In webhook scenarios FlowGuard **simulates a webhook provider** (the role
Stripe or GitHub would play): it delivers synthetic events, with controlled
duplication, delay, ordering, timeouts and retries, to the **receiver under
test**, then reads the receiver's resulting business state.

FlowGuard does **not** test a real provider's internal retry scheduler,
delivery guarantees or timing. Retries, delays and ordering are exactly what
the config declares, so the same config always produces the same requests in
the same order.

Like v0.1, webhook scenarios are for local mocks and test environments you
own. Every request goes through the `allowed_hosts` and redirect policy.

## Decisions

| # | Decision |
| - | -------- |
| 1 | Webhook fields are flat on `Scenario`, validated per `kind`. |
| 2 | Optional HMAC-SHA256 signing is part of Milestone 2 (v0.3.0; originally planned for v0.2). |
| 3 | The mock server keeps a single `-safe` flag (buggy by default). |
| 4 | `expect.status` takes exact integers only. |
| 5 | An omitted `expect.outcome` defaults to `delivered`. |

## Architecture

```
flowguard test
  config.Load (strict)                        reused; schema extended
  scenarios.RunWebhook(ctx, client, base, sc)
    1. runSetup                               reused
    2. for each delivery, in declared order (sequential):
         [M2] wait for delay
         encode the event body once  ([M2] sign it)
         runner.DoBody                        allow-list, redirects, redaction reused
         classify: delivered (2xx) | rejected (other status)
                   [M2] timeout, retry with fixed backoff
    3. observe: send observe.request          reuses runner.Client.Do
       [M2] poll until assertions hold or wait expires
    4. assertions: per-delivery expectations + final state
  report.Build / CLI output                   reused; optional fields added
```

No scenario-kind registry or plugin interface: a `switch` on `kind` is enough
for two kinds. The only test seam planned is a package-level `sleep` function
(Milestone 2) so delays and backoff can be tested without waiting.

## Configuration

Fields are valid only for `kind: webhook`; strict validation rejects them in
an `idempotency` scenario, and rejects `request`, `repeat`, `assert.status`
and `assert.business_effect_count` in a `webhook` scenario.

### Milestone 1 schema

```yaml
- name: duplicate-delivery
  kind: webhook
  setup:                                  # existing, optional
    - {method: POST, path: /_test/reset}
  endpoint:                               # the receiver under test
    method: POST
    path: /webhooks
    headers: {X-Source: flowguard}        # optional, sent with every delivery
  events:                                 # sent exactly as written
    - id: evt_paid_1                      # unique; used by deliveries and reports
      headers: {X-Event-Type: order.paid} # optional, per event
      json: {id: evt_paid_1, type: order.paid, data: {order_id: ord_1, amount: 100}}
  deliveries:                             # run in this order
    - event: evt_paid_1                   # expect omitted -> outcome: delivered
    - event: evt_paid_1
      expect: {outcome: delivered, status: 200}
  observe:                                # how final business state is read
    request: {method: GET, path: /_test/orders/ord_1}
  assert:
    state:                                # dot-path -> expected scalar
      status: paid
      charges: 1
```

Validation rules (Milestone 1):

- `endpoint.method` and `endpoint.path` are required; `endpoint.json` is
  rejected (bodies come from events).
- At least one event; ids are non-empty and unique; `json` is required.
- At least one delivery; each `event` must name a declared event.
- `expect.outcome` is `delivered` or `rejected`; `expect.status` is
  100-599 and must agree with the outcome (2xx for `delivered`, non-2xx for
  `rejected`).
- `observe` and `assert.state` must be given together; `observe.request`
  needs `method` and `path`, and the method must be `GET` (reading state
  must not change it; other methods are rejected, never rewritten).
  `observe.request.json` is rejected: the state request has no body.
- `assert.state` keys are dot-paths with non-empty segments
  (`order.status`, `charges.0.amount`); values are scalars (string, number,
  boolean or null).
- At most 100 events and 100 deliveries per scenario.
- Every header map of a webhook scenario (`setup[].headers`,
  `endpoint.headers`, `events[].headers`, `observe.request.headers`) is
  checked at load time: names must be HTTP tokens, values may not contain
  control characters other than tab (no CR/LF injection), the same header
  may not appear twice in different case (merging would be
  non-deterministic), and transport-managed headers (`Host`,
  `Content-Length`, `Transfer-Encoding`, `Connection`, `Keep-Alive`,
  `Proxy-Connection`, `TE`, `Trailer`, `Upgrade`) cannot be set. A header
  net/http would refuse is therefore a config error, never a runtime error
  after setup has run. Errors name the header, never its value.
  Idempotency scenarios keep v0.1.1 validation. Ownership of the signature
  header is defined with signing (T14).

### Milestone 2 additions

Until Milestone 2 implements them, these fields are **unknown and
rejected**, so a config cannot declare behavior FlowGuard would silently
skip.

```yaml
  signing:                                # optional
    algorithm: hmac-sha256
    header: X-Signature
    secret_env: FLOWGUARD_WEBHOOK_SECRET  # env var name; secrets never in YAML
    encoding: hex                         # hex | base64
    prefix: "sha256="                     # optional
  deliveries:
    - event: evt_paid_1
      delay: 300ms                        # wait before the first attempt
      timeout: 100ms                      # per-attempt deadline (<= 10s)
      retry: {max_attempts: 3, backoff: 50ms, on: [timeout, 5xx]}
      expect: {outcome: timeout, attempts: 3}
  observe:
    wait: {timeout: 2s, interval: 100ms}  # poll until state assertions hold
```

Caps: delay <= 30s, timeout <= 10s, backoff <= 30s, max_attempts <= 10,
observe wait <= 60s, and a scenario's worst-case runtime (computed at load
time) <= 5 minutes.

## Delivery semantics

| Concept | Semantics |
| ------- | --------- |
| Event body | `json.Marshal`ed once per delivery (sorted keys), so retries resend identical bytes and signatures. |
| Order | Deliveries run strictly in list order; a duplicate is a repeated entry. |
| Outcome | `delivered` (2xx) or `rejected` (other status); `timeout` in Milestone 2. |
| Runtime error | Connection refused, allow-list or redirect violation, bad URL: never retried, aborts the scenario, exit 2. |
| Expectation | Checked against the final attempt; a mismatch is an assertion failure, exit 1, and the remaining deliveries still run. |
| Headers | `endpoint.headers` are defaults; `events[].headers` override them by case-insensitive name, and each header is sent once. Content-Type defaults to `application/json` unless either map sets it. |

## Observing business state

- `observe.request` is sent through `runner.Client.Do` (not `GetJSON`,
  which cannot honor the declared method and headers), so the allow-list,
  redirect policy, timeouts, cancellation, redaction and 1 MiB response
  limit apply.
- The body must be exactly one JSON value; trailing data is an error.
- A transport error, non-200 status or non-JSON body from the state
  endpoint is a **runtime error, exit 2** (as with the v0.1 effect-count
  endpoint).
- A state value that does not match is an **assertion failure, exit 1**. A
  missing path fails and names the path.
- Values are compared by JSON type and value. Observed numbers are decoded
  with `UseNumber`; expected numbers are read from their YAML literal
  (`config.StateAssertions`): integers that fit in 64 bits stay Go integers,
  and every other number becomes an exact `json.Number` instead of a
  rounded float64. Both sides are compared as exact rationals
  (`math/big`), so `1`, `1.0` and `1e0` are equal, YAML `0.1` equals JSON
  `0.1`, `0.10000000000000001` does not, and large integers keep full
  precision. Exponents are limited to ±1000 and numbers to 2000 digits
  (config error otherwise). `"1"` never equals `1`, and a missing path
  never counts as null, zero, false or "".
- Paths walk object keys and non-negative array indexes (`items.0.sku`).
  A key that itself contains a dot cannot be addressed in v0.2.
- Only asserted paths are reported. If any path segment looks sensitive
  (`redact.SensitiveName`: token, secret, password, api_key, signature,
  ...), both expected and actual are shown as `REDACTED`. Other string
  values pass through `redact.Text` and are truncated to 200 characters;
  objects and arrays are shown as `<object>` / `<array>`. Comparison
  always uses the raw values.

## Mock receiver

`examples/mock-server` gains, behind the existing `-safe` flag:

| Endpoint | Behavior |
| -------- | -------- |
| `POST /webhooks` | `{id, type, sequence?, data{order_id, amount?}}`; types `order.created`, `order.paid` (needs a positive integer `amount`), `order.cancelled`. 200 `{"received":true,"applied":bool,"reason"?}`; 400 malformed JSON, 413 over 1 MiB, 422 invalid or missing field or unsupported type |
| `GET /_test/orders/{id}` | 200 `{"id","status","charges","processed_events":[...],"last_sequence"}`; 404 for an unknown order |
| `POST /_test/reset` | also clears orders, processed event ids and sequences |

Ids are 1-128 characters from `A-Z a-z 0-9 _ . : -`. The first valid
event naming an order creates it, whatever its type. Rejected events change
nothing and are not remembered.

| Buggy (default) | `-safe` (rules checked in this order; ignored events answer 200 with `applied: false`) |
| --------------- | ------- |
| No dedupe: a duplicate `order.paid` charges twice | `duplicate`: a processed event id has no effect |
| Applies stale events: a lower `sequence` overwrites status and `last_sequence` | `stale`: `sequence` at or below `last_sequence` is ignored |
| A late `order.created` rolls status back; a payment after cancellation charges and reopens | `order cancelled`: cancelled is final; `order.created` never changes an existing status |
| Every distinct `order.paid` charges | `already paid`: an order is charged at most once |
| [M2] Applies the effect, then fails (`X-Mock-Fail-Times`) | Fails without applying |

Milestone 2 adds the mock-only headers `X-Mock-Delay-Ms` (apply, then
respond late) and `X-Mock-Fail-Times` (respond 500 to the first N attempts),
and an optional `-secret` to verify signatures.

## Reporting and exit codes

Terminal output for a webhook scenario lists each delivery, then every
assertion (deliveries first, then state), then any runtime error:

```
Running: duplicate-delivery
  delivery[0] evt_paid_1: 200 delivered
  delivery[1] evt_paid_1: 200 delivered
  [PASS] delivery[0].outcome
  [PASS] delivery[1].outcome
  [FAIL] state.charges: expected 1, got 2
  [PASS] state.status
```

Assertions are printed before `[ERROR]`, so results gathered before a
runtime error stay visible. Idempotency output is unchanged.

- New step fields `event_id` and `outcome`, both `omitempty`, written
  after `index` and `status`. In Milestone 1 each delivery is one step, so
  a step's `index` is its delivery index and `delivery[i]` rules describe
  `steps[i]`. A delivery that failed at runtime has `error` and no
  `outcome`. Milestone 2 adds `delivery`, `attempt` and `delay_ms` (also
  `omitempty`) once retries make steps per attempt.
- New assertion rule names: `delivery[i].outcome`, `delivery[i].status`,
  `state.<path>` (and `delivery[i].attempts` in Milestone 2).
- Exit codes are unchanged: 0 all passed, 1 an assertion failed (including
  final state), 2 config or runtime error (including state-read transport
  errors).

## Compatibility

- v0.1.1 configs load and run unchanged; `version: 1` stays.
- Idempotency reports and terminal output stay byte-identical, enforced by
  a golden test (ignoring time fields).
- The runner API only gains additions (`DoBody`; `IsTimeout` in M2); `Do`
  keeps its signature and behavior.
- No new module dependencies.

## Security, performance and determinism

- Signing secrets come only from an environment variable and never appear
  in output. Docs: use test-environment secrets only.
- Deliveries and state reads use the existing allow-list and per-hop
  redirect checks.
- Caps and a load-time worst-case runtime check stop configs from hanging
  CI; Ctrl-C cancels delays and polling (`signal.NotifyContext`).
- No randomness, jitter or concurrency. Timing-based examples keep >= 3x
  margins and use polling where processing is asynchronous.
